# P15 M0 at 300 MHz — Pico 2 W, 2026-08-29

**The gate reading.** `hw.setcpu "fast`, 60 frames a point, `splitscreen`,
present with `refresh`. Companion to the 150 MHz run
([`p15m0-normal-2026-08-29.md`](p15m0-normal-2026-08-29.md)).

> ### The gate fails: 106.0 ms against 50 ms.
>
>     300 MHz:  frame = 35.1 + 6.44 n     n=11: 106.0 mean, 109 worst
>
> That is **9.4 fps** where §15.3 asked for 20, and **2.8× the §15.2 estimate
> of 38 ms**.

## The 150 MHz projection was right to 0.2 %

Worth recording, because it means the scaling method can be trusted for the
next question rather than re-measured.

| | projected from 150 | measured at 300 | error |
|---|---:|---:|---:|
| logic | 55.1 ms | 55.28 | 0.3 % |
| drawing | 32.8 | 31.98 | 2.6 % |
| body | 87.9 | 87.13 | 0.9 % |
| present | ~17.9 | 18.87 | 5.1 % |
| **frame @ 11** | **~105.8** | **106.0** | **0.2 %** |
| slope | 6.5 ms/robot | 6.44 | 0.9 % |

P13 M0's measured **2.059** interpretation ratio transfers to a Pico 2 W
unchanged. The present under-projected because it moves slightly *more* than
P13's split did (21.95 → 18.85 here, 1.16×, against P13's 19.62 → 18.70, 1.05×).

## The diagnosis: the unit table was right, the statement counts were not

This is the whole finding, and it is sharper than "the estimate was low".

| unit | §15.1 predicted at 300 | measured | error |
|---|---:|---:|---:|
| arithmetic statement | ~24 µs | **24 µs** | **0 %** |
| bare `repeat` iteration | ~2.4 µs | **2.5 µs** | 4 % |
| present, `splitscreen` | 18.70 (P13, once corrected) | **18.85** | 0.8 % |

**Every unit §15.2 multiplied was right.** The 2.8× miss is therefore *entirely*
a counting error — §15.2 budgeted the wrong number of statements, not the wrong
price for one:

| | §15.2 statements | implied by measurement | factor |
|---|---:|---:|---:|
| one robot, drawn | 15 | **~45** | 3× |
| one robot, thought | ~30 | **~180** | 6× |
| drawing, all | 247 | ~1160 | 4.7× |

`.setitem` on an eleven-element list is **33 µs**, against `item`'s **8 µs** —
**4× the read**, and 1.4× an arithmetic statement. §16 asked for that number.

## Where the 106 ms is

| | ms | share |
|---|---:|---:|
| logic | 55.28 | 52 % |
| drawing | 31.98 | 30 % |
| present | 18.87 | 18 % |

    slope   6.44 ms a robot   (logic 4.42, drawing 2.02)
    floor  35.13 ms           (present 18.87, body 16.26)

**The budget allows 2.3 robots.** `(50 − 18.87 − 16.26) / 6.44`. Berzerk needs
eleven.

To fit eleven, the per-robot cost must fall from 6.44 ms to **1.35 ms — 4.8×**.

## Q1 — the erase strategy, at the clock that matters

| | 4 robots | 11 robots |
|---|---:|---:|
| erase in place — body / present | 52.33 / 4.22 | 110.58 / **8.42** |
| clear + redraw — body / present | 42.43 / 18.75 | 86.70 / **18.98** |
| **frame** | **56.55** vs 61.18 | 119.00 vs **105.68** |

**The verdict inverts with the robot count, which neither §3 nor the 150 MHz
run showed.** At 4 robots erase-in-place *wins* by 4.6 ms; at 11 it loses by
13.3. The crossover is around six robots.

The mechanism is clear in the numbers: in-place buys a present saving that
**grows slowly** (18.98 → 8.42, a fixed ~10 ms ceiling set by the canvas) and
pays a second actor pass that **grows with n**. So the strategy that wins
depends on how full the room is, and §3's "6.8 against 0.8, not close" was
comparing two numbers that were both wrong and whose ordering is not even fixed.

This does not change the M0 decision — 11 robots is the gate's case, and there
clear-and-redraw wins — but it should be re-read if the robot count is ever cut,
which is exactly what §17 is now being asked to consider.

**§15.4 flagged the wrong two numbers.** The pair loop is 1.8× low — real, and
the smallest miss on the page. The model dispatch it worried about does not
appear at all: `time.robot` is 2.01 ms and the series slope's drawing half is
2.02, so the `run`-over-five-names dispatch costs nothing measurable. That
prediction held exactly.

## Board and thermals

Pico 2 W, no PSRAM. **36.4 → 39.3 °C** over the run at 300 MHz — a 2.9 °C rise,
against P13's 2.6 on a Plus 2 W. Not a constraint.

Word table: **14,532 bytes free at start**, against 21,608 on the 150 MHz run's
board — worth noting for §18, since the harness is the same size either way.
Frame allocation is **0 cells and 0 word bytes** warm.

## What the harness dropped, and which way

To hold the scene still (so erase-in-place is comparable), the timing path
computes positions and discards them: **19 `.setitem` calls a frame** at eleven
robots. At 33 µs that is **0.63 ms the real frame would pay and this one did
not** — so every figure above is optimistic by that much, and the gate misses by
more than it says.
