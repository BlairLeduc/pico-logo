# P15 M0 at 150 MHz — 2026-08-29, board not recorded

The first reading of `tests/logo/p15m0`, and the first that reached the end:
the run before it died with `out of space in rob.left` (B52). 60 frames a
point, `splitscreen`, present with `refresh`.

**It was taken at `normal`.** `p15m0.cpu` defaults to `"same` and the board was
at 150 MHz, so **this is not the gate** — §15.3's gate is a 300 MHz number.
Everything below is the 150 MHz reading with the 300 MHz projection beside it,
scaled by P13 M0's *measured* 2.059 on the body and leaving the present alone,
because the present is the SPI wire (P13 measured it moving 19.62 → 18.70 across
the same doubling). The harness now says this for itself rather than leaving it
to be noticed.

The board is not recorded because the report did not carry it, and this run is
the only one of the series that is unlabelled — every later run was confirmed a
**Pico 2 W**, and this was almost certainly the same board, but "almost
certainly" is not a reading. That gap is why the harness now reports what it
can: `tls?` is the only fixed hardware capability the language exposes, so it
separates the Plus 2 W, and the other two are noted by hand.

## The verdict

| | design §15.2 (at 300) | measured (150) | projected (300) | factor |
|---|---:|---:|---:|---:|
| logic | 17.1 ms | 113.55 | **55.1** | **3.2×** |
| drawing | 6.8 | 67.52 | **32.8** | **4.8×** |
| body | 24 | 181.07 | **87.9** | **3.7×** |
| present | 14.0 | 18.83 | ~17.9 | 1.3× |
| **frame @ 11** | **38** | **199.9** | **~106** | **2.8×** |

    150 MHz:  frame = 53.3 + 13.42 n     n=11: 199.9 mean, 208 worst

> **The gate fails, and no clock can save it.** The gate is 50 ms at 300 MHz.
> The **slope alone** is 13.42 ms a robot at 150, so **6.5 ms at 300** — and
> eleven of those is **71.6 ms before the floor is added at all**. A frame with
> a zero-cost floor still misses the gate by 43 %.

To reach 50 ms at 300 with an ~18 ms present, the body must be ≤ 32 ms, which
is 66 ms at 150. It measured **181**. That is a **5.6× reduction**, which is not
an optimisation.

## §15.1's present row is wrong, and the error is a mislabelled column

The design's unit table says:

| | 150 MHz | 300 MHz |
|---|---:|---:|
| present, `splitscreen` (240 rows) | 19.2 ms | **~14.0 ms** ← invented |
| present, `fullscreen` | 26.45 ms | 18.70 ms ← **not fullscreen** |

**18.70 is P13 M0's measured `splitscreen` at 300 MHz**, not fullscreen —
[battlezone-design §12.3](../battlezone-design.md) says it in words: *"the
present itself moves **19.62 → 18.70 ms**"*, of the split present. §15.1 put
that figure in the fullscreen row and then "derived" a splitscreen-at-300 of
14.0 from a pair that never existed.

So the design has been budgeting **14.0 ms** for a present that P13 had already
**measured at 18.70** on a board. This run reads **21.95 at 150** against P13's
19.2–19.62 — higher because the dirty region differs (a Berzerk room is drawn
edge to edge; Battlezone's scene is not) — and **fullscreen reads 26.45, which
matches Battlezone exactly**, so the instrument is fine and the table was not.

The practical consequence is small next to the body: the present is **9 %** of
this frame. Which is itself the finding — see below.

## Q1 — the erase strategy: clear-and-redraw, but §3 argued it wrongly

| | 4 robots | 11 robots |
|---|---:|---:|
| erase in place — body / present | 108.07 / 4.35 | 228.52 / **8.97** |
| clear + redraw — body / present | 87.53 / 19.60 | 178.95 / **19.55** |
| **frame** | 112.42 vs **107.13** | 237.48 vs **198.50** |

**The verdict holds and both of §3's numbers are wrong.** §3 predicted in-place
would pay ~6.8 ms of extra drawing to buy back nothing, because *"a present that
touches most rows costs about what a present that touches all of them costs"*.
Measured, it pays **49.6 ms** of extra drawing and buys back **10.6 ms** — so
**the dirty-tile tracker is far better at scattered figures than §3 assumed**.
Eleven robots over five columns and three rows present in 8.97 ms against a
full-canvas 19.55.

That is worth keeping, because it is the opposite of the reason §3 gave: the
present is not the problem, and a strategy that avoids `clean` really does get
most of it back. In-place loses only because *drawing* is five times what the
design thought — and if drawing gets cheaper, §3 has to be asked again.

## Q4 and Q5 — the pieces

| | design | measured (150) | factor |
|---|---:|---:|---:|
| collision pair loop, 7 × 11 | 4.0 ms | **14.91** | 3.7× |
| eleven robots drawn | 4.6 | **45.1** (4.1 each) | **9.8×** |
| border + eight interior walls | 0.8 | **7.33** | 9.2× |
| one room generated | — | 15.21 (once a room) | — |
| `.setitem`, eleven-element list | — | **65.5 µs** | — |
| `item`, eleven-element list | ~16 µs | 22 µs | 1.4× |

**`.setitem` is three times `item`** and 1.5× an arithmetic statement. §16 asked
for this number because nothing in the tree had it. Berzerk does ~40 a frame:
2.6 ms at 150, 1.3 at 300 — real, but not the lever, because the lever is the
statement count itself.

**Calibration**: arithmetic statement **45 µs**, bare `repeat` iteration
**7.5 µs**. The first sits in P11 M0's 42–44.5 range (and below B51's 53); the
second is above P11's 4.5–7.

**Thermals**: 35.3 → 33.5 °C. It cooled, at 150 MHz.

**Storage**: nodes flat at 18,220 across the whole run. Word bytes 21,608 →
20,408, recovering to 20,872 — that is the report's own sentences, not the
frame: `alloc.per.frame` reports **0 cells and 0 word bytes** over 100 warm
frames, which is B52 closed.

## What this changes

**The frame is 90 % interpretation.** Body 181 against present 19. §4 spent a
section on the split screen being *"worth about 4.7 ms"* and §15.1 spent a
derivation on the present; both were optimising the 10 %. Every lever that
matters is in the body.

**§16's headline conclusion is overturned.** It says *"**Berzerk needs no
interpreter change to ship.**"* That was argued on the right grounds — there is
no trigonometry, and arrays buy ~0.4 ms — and it is wrong anyway, because the
cost is not in any one primitive. It is in the sheer number of statements: a
robot costs **4.1 ms to draw** (~45 statements) and **9.1 ms to think**
(~190 statements), and eleven of them is the whole budget twice over.

**The two numbers §15.4 flagged were both wrong, and neither was the problem.**
The pair loop is 3.7× low and the model dispatch was avoided successfully — the
`run`-over-five-names cost is not visible. The number nobody flagged is the one
that broke it: **`iq` calls `cell.at` four times per robot per frame**, and
`cell.at` is ~10 arithmetic statements (two divides, two `int`s, four clamps).
That is ~40 statements a robot a frame for wall probing alone. §6.3 sold the
cell lookup as *"four statements, no pixels"*; it is four *lookups*, and each is
ten statements.

Suspected but not separated by this run: **`arc` is not cheap**. Otto is two
arcs and the man's head is one, and drawing at 11 robots leaves ~15 ms for the
man, Otto and seven bolts where a statement count predicts ~4.
