# Bugs

Tracks defects in Pico Logo — past, present and future. A **bug** here is
behaviour that contradicts
[`reference/Pico_Logo_Reference.md`](../reference/Pico_Logo_Reference.md),
silently loses or corrupts data, or hangs/crashes the interpreter.

Sibling document: [`roadmap.md`](roadmap.md) tracks
*features* — new primitives, designs, milestones and performance work. If an
item adds capability it belongs there; if it means "this doesn't work as
documented", it belongs here.

**Status legend:** `open` · `in progress` · `fixed` · `won't fix`

**Severity:** `high` (data loss, crash, hang, unusable feature) · `medium`
(surprising wrong behaviour with a workaround) · `low` (cosmetic or narrow
edge case)

### B45 — A failed `malloc` panics the board instead of raising an error

Any heap allocation that fails on device brings the interpreter down with
`*** PANIC *** Out of memory` and a board that must be power-cycled, rather
than reporting an error the user can recover from. The SDK's `__wrap_malloc`
(and `__wrap_calloc`) call `panic()` when the underlying allocation returns
NULL, which is `PICO_MALLOC_PANIC`'s default:

```
100224b0 <__wrap_malloc>:
  bl   <malloc>
  cbz  r0, 100224c6      @ NULL -> panic
  ...
  bl   <panic>
```

Every NULL check behind an allocation on device is therefore dead code —
including `repl_init`'s, whose failure path `main` handles by printing
`Out of memory` and idling, and the editor's, which is written to degrade to
"undo is not available" rather than to crash. The reachable cases are all
runtime ones on a board with no PSRAM, where the heap is tens of KB: `sort` or
`fput` on a large list (`malloc(count * sizeof(...))`), the first `http.get`
(~2 KB), the first `tile` use (4 KB bank + 4 KB map), `syntax_highlight` on a
long line.

- **Status:** open. Found 2026-08-20 while diagnosing B44, which is what made
  the panic visible: the fix there removes the *startup* overcommit, but the
  runtime ones are untouched. The fix is `PICO_MALLOC_PANIC=0` in the device
  build plus an audit that every allocation site really does handle NULL —
  the compile definition alone would turn a panic into a wild pointer at any
  site that does not.

### B32 — A procedure body over 254 lines re-runs statements

A procedure whose body is longer than 254 lines runs a few of its statements
twice. The count is small and grows with the body: one extra at 255 lines, two
at about 525, three at about 790 — roughly one more every ~270 lines. Nothing
is reported; the procedure simply does slightly more than it says.

The trigger is the **number of newline-separated lines**, not the number of
statements or the size of the text: 250 lines carrying three statements each
(750 statements, 21 KB) run exactly 750 times, while 255 lines of one statement
run 256. The first divergence landing on 255 points at a byte-sized count or
index somewhere in how a body is stored or stepped.

Reproduce without any device or editor involvement — this is the interpreter
itself, not `edit`:

```c
static char big[32 * 1024];
size_t len = (size_t)sprintf(big, "to big\nmake \"n 0\n");
for (int i = 0; i < 255; i++)
    len += (size_t)sprintf(big + len, "make \"n :n + 1\n");
sprintf(big + len, "end\n");

proc_define_from_text(big);
run_string("big print :n");   // prints 256
```

- **Status:** open. Found 2026-08-17 while sizing the editor buffer from PSRAM
  (roadmap: larger editor buffer), which is what made 255-line procedures
  reachable — the 8 KB SRAM buffer could not hold one. `edit` and `editfile`
  are not implicated: the same body defined directly misbehaves the same way.
  It reproduces on the host under ASan and UBSan with no diagnostic, so it is a
  logic error rather than a memory one. Note that it is **build-sensitive**: the
  same source failed in one host build directory and passed in another, so a
  green test run is not evidence the bug is gone.
- **Impact:** high — silently wrong results in exactly the long procedures a
  256 KB editor buffer invites. `tests/test_primitives_editor.c` keeps its large
  definition under 250 lines to steer around it.

### B19 — Collision tests ignore the wrapped playfield

Every box test in `logo/games/asteroids` compares raw coordinates, so two
objects three steps apart *across* an edge read as 317 steps apart and never
collide. Found while instrumenting B18: a ship at x = 158 and a saucer shot at
x = −159 pass through each other.

The playfield wraps for **drawing** (the engine's `wrap` splits a segment across
the edge) and for **motion** (`wrapc` and `setspeed`), so the picture is right
and only the arithmetic is wrong. It affects every pair — shots on rocks, rocks
on the ship, the saucer on anything — in a band a few steps wide at each edge.

- **Status:** open, and not obviously worth fixing. The correction is a wrapped
  distance (`if d > 160 [make "d 320 - d]`) on both axes of every test, which is
  two comparisons and a subtraction **per pair per frame** — about 24 extra
  statements a frame at twelve rocks, against a frame that is already at its
  budget (the design's §12f). What it buys is correct behaviour in perhaps 5 %
  of the field, in a game where the objects that matter are usually near the
  middle. Worth revisiting if the collision pairs ever get cheaper.
- **Found:** 2026-08-12, while probing B18.

### B6 — `penreverse` ignores pen size (always 1 px)

`penreverse` toggles pixels, so overlapping thick stamps would toggle shared
pixels twice and speckle the line. Thick reverse drawing is therefore left at
1 px and documented as a limitation rather than implemented.

- **Status:** won't fix for now. A future thick-reverse pass would delta-stamp
  only the pixels the previous stamp did not cover, or fill per-scanline spans.
- **Found:** 2026-07-18, with `setpensize` / `pensize`.

## Reporting a bug

1. Write a failing test first (`tests/test_<module>.c`, mock device) that
   reproduces it — see the Unit Testing rules in
   [`CLAUDE.md`](../CLAUDE.md).
2. Add a row to **Open** above with the next `B<n>` ID and a detail section.
3. Fix it, run `ctest --preset=tests`, then move the row to **Fixed** with the
   date and PR.

Bugs that cannot be reproduced on the host (real lwIP or cyw43 timing, PSRAM,
audio DMA) should say so explicitly and record how they were validated on
hardware instead.
